F00 · Project setup

Status: In review

Goal

Before the first product feature can be built, there is no project to build it in. There is no agreed repository layout, toolchain, CI, plugin structure or documentation convention. Every later feature, mostly written by coding agents, would otherwise make its own choices, and packaging or plugin problems would surface in the middle of designing something else.

With this feature, tandem has a public repository in which a developer or an agent clones, runs one command, and has formatting, linting, type checking, architecture checks, unit tests with coverage and end-to-end tests working the same way on their machine and in GitHub Actions. main only changes through green, squash-merged pull requests. The Claude Code plugin loads straight from the working tree. A small throwaway placeholder gives every tool and every CI job real code to run against. A README, a contribution guide, an architecture document and the first architecture decision records explain how to work in the repository. The next feature starts by deleting the placeholder, not by setting anything up.

Non-goals

  • How tandem works inside: no session loop, storage, editor or collaboration. The placeholder only exercises the tooling and is deleted by the next feature (Placeholder).
  • Reusing spike code. The spikes were throwaway experiments; their code is never copied in as the design.
  • Releases and the public face: versioning, the release workflow, publishing to a marketplace, dependency update automation, the public README with screenshots, a changelog, issue templates, code of conduct and SECURITY.md belong to F12 · Publishing. F00 only makes the plugin loadable from the local working tree and prepares the layout the release will use.
  • The product name. “tandem” is a working name that is already taken by a similar project; F00 keeps it cheap to change (Renaming) but does not choose a new one.
  • Coding tools other than Claude Code.
  • Product security. The placeholder server listens on 127.0.0.1 without authentication; endpoint protection and sanitising are F11 · Security & sanitising. F00 only sets a security baseline for CI (CI on GitHub).
  • Windows. Only macOS and Linux are supported for now; the plugin's entry point is a bash script.
  • UI component library, CSS approach and theming: decided by F04 · Editor UI, which designs the editor they are for.
  • CI on macOS: decided by F01 · Session loop, where process handling and file watching first make the platforms differ.
  • Proving that the heavy runtime libraries (Hocuspocus, Yjs, an HTML parser) bundle into the plugin and that server and browser share one pinned @tiptap/y-tiptap: required of the features that introduce them (F02, F05).

Functional design

Someone — the maintainer, a coding agent, later other contributors — clones the public repository, installs mise and runs mise install. That one command installs the pinned Node, pnpm and Claude Code versions, the project's dependencies, the browser for end-to-end tests and the git hooks. They work on a branch. Every commit formats and lints the staged files and type-checks the whole project if code changed; every push runs the unit tests. mise run check runs everything locally, and mise run claude-dev starts Claude Code with the plugin under development loaded. They open a pull request whose title follows Conventional Commits. CI shows lint and type errors on the changed lines, enforces test coverage on every touched file and runs the end-to-end test; only when everything is green can the pull request be squash-merged into main. Agents never push and never skip hooks unless the user explicitly asks.

Setting up

The only thing to install by hand is mise; to try the plugin interactively, the developer also needs their own Claude Code. Everything else is pinned by the repository, including the Claude Code version the checks use. mise install installs the tools and then runs mise run setup, which installs the dependencies, downloads the Playwright browser and installs the git hooks. mise only runs that step when it actually installed a tool, so after a pull that changed dependencies the developer runs mise run setup by hand (Toolchain and versions). The repository works on macOS and Linux.

Tasks

Every tool that checks or formats code has one task for local use and one for CI. The local task fixes what the tool can fix and prints its findings; the -ci variant never changes files, fails on any finding and writes a report CI can show. Three aggregate tasks combine them: check-fast runs everything except the tests, check runs everything including unit and end-to-end tests, and check-ci is exactly what CI runs. Tools that neither check nor format get one plain task each.

Git hooks

Hooks give feedback before anything leaves the machine; CI is still the gate. Each hook only runs a tool when a file that can change the tool's result is involved — but a tool whose result depends on the whole code base runs on the whole code base, because an edit to one file can break another.

  • Before each commit, for the staged files: format and lint with fixes, and the fixed files are staged again. If any TypeScript or Vue file or a TypeScript config is staged, the whole project is type-checked. If anything under src/ is staged, the import rules are checked; if anything under plugin/ is staged, the plugin is validated.
  • Before each push: the unit tests, if the pushed commits change anything under src/. Coverage is not measured in hooks.
  • End-to-end tests and agent tests never run in hooks.

The hooks have a time budget: about 10 seconds before a commit and about 60 seconds before a push, for a normal change. If they get slower, the tools they run are made faster, or the slowness is accepted; type checking is never moved out of the commit hook, because cross-file type errors are cheapest to fix right away. When a hook fails, the cause is fixed; nobody skips hooks, and agents only do so when the user explicitly asks.

Changing main

Every change reaches main through a pull request; nobody pushes to main directly, and force-pushes are blocked. A pull request can be merged only when all required checks are green, and only as a squash merge, so one pull request becomes exactly one commit on main whose message is the pull request's title. The title must follow Conventional Commits (feat(cli): add serve command, fix(server): …); a check fails the pull request otherwise. Commits inside a branch are free-form. While the maintainer works alone with agents, no approvals are required — GitHub does not let anyone approve their own pull request, so a required approval would block every merge; required reviewers can be added later without changing anything else. Agents work on branches, never push unless the user asks, and the user merges.

What CI reports

CI runs on every pull request to main and on every push to main. Findings appear where they are: lint and type errors as annotations on the changed lines of the pull request, a short summary per run (which checks passed, test counts, failures), and, when an end-to-end test fails, the Playwright report with trace and screenshot attached to the run.

Coverage is a gate: every file a pull request adds or changes must reach at least 80 % line coverage and 80 % branch coverage on its own, measured from unit tests. A new file without any test counts as 0 % and fails the gate. Changing one line in an old, poorly tested file means raising that whole file to 80 %. On the push to main after a merge, the same rule is applied to the files of that one squash commit.

Agent tests run only on demand: started by hand or by a pull-request label only the maintainer can set. They are not a required check, because they cost model usage and their results can vary between runs. Pull requests from forks never get the Claude credential they need.

Trying the skeleton

The placeholder is the smallest thing that touches every tool: tandem hello prints a greeting, and tandem serve starts a local server, prints its URL and shows a page that fetches the greeting from the server. The server picks any free port unless --port is given, so several runs never collide; the URL is read from the output. Ctrl+C stops it. Every placeholder file starts with PLACEHOLDER (F00) — delete in the next feature, and the next feature deletes all of them before it builds anything.

If Node is missing or older than 24, tandem stops before doing anything and says which version is needed and where to get it (Build and bundling).

Developing the plugin

mise run claude-dev builds everything and starts Claude Code with the plugin loaded from the working tree for that one session; nothing is installed and nothing is written to the user's settings. After a change, the developer rebuilds and runs /reload-plugins in that session. Normal Claude Code sessions in this repository — including the agents writing tandem — never have the development plugin active, so its hooks cannot get in the way of working on the project itself. The placeholder plugin has a stub skill that tells Claude to run tandem hello, one hook that does nothing but leave a trace, and one agent test checking that Claude runs tandem hello when asked to greet using the plugin.

Documentation and conventions

All documentation lives in docs/, and docs/ is never touched by the code formatter: its HTML files are tandem documents whose formatting tandem itself will own.

  • docs/features/ — the feature pages, which become specs. A spec is written once and not updated after its feature is implemented; it must be self-contained. It may mention a spike as a soft reference — the branch spike and a path, as text — but never relies on a spike or on the spike summary to explain its content.
  • docs/architecture/ — the architecture document, describing the system as it is now. Every feature's implementation updates it.
  • docs/adr/ — architecture decision records: the history of decisions that bind later features, and why they were made.

Brainstorming journals are working notes that keep decisions from getting lost while a spec is being designed. They sit next to the feature page while it is written and are never committed; every accepted decision ends up in the spec, and the binding ones in an ADR. CONTRIBUTING.md holds the rules for everyone, human or agent; CLAUDE.md only says what tandem is, points to CONTRIBUTING.md and adds the rules for agents. A feature is done only when its living documents are updated; a pull-request template with three checkboxes — tests, living documents, ADR if a binding decision changed — makes that visible on every pull request.

Renaming

The working name appears in code exactly once, as a constant, and otherwise only where a file name or a manifest cannot refer to a constant: the CLI entry point plugin/bin/tandem, the skill folder, the plugin and marketplace manifests and package.json. The README lists these places as the renaming steps, so a rename is a short, mechanical pull request.

Context

F00 is the foundation the other features are built on; it has no role in tandem at runtime, and its placeholder is deleted by the next feature. Around it are the people and agents working in the repository, the tools and services the setup relies on, the machine of a future plugin user, and the later features that inherit the setup.

Assumptions and constraints

  • Developers and plugin users run macOS or Linux. A Windows user would need a different entry point and CI job.
  • Plugin users have Node 24 or newer. Node 24 is supported until about April 2028; the minimum must be raised before then.
  • The repository is public. On GitHub's free plan, rulesets and protected branches only work for public repositories, and Actions minutes are free only there; a private repository would need a paid plan for the gate to hold.
  • TypeScript stays on version 6 until vue-tsc and typescript-eslint support TypeScript 7, whose native compiler has no stable programmatic API yet. The move is a separate change.
  • Claude Code's plugin features behave as documented in November 2026: --plugin-dir loads a plugin in place, files in a plugin's bin/ are on the Bash tool's PATH while the plugin is enabled, claude plugin validate and claude plugin eval work as described, and a marketplace entry can point at a subfolder of a branch. Points not yet verified are listed under Must prove first.
  • The next feature deletes the placeholder before building its own code; nothing may depend on it.

Solution design

The repository is one pnpm package with four source folders whose import rules are enforced by dependency-cruiser. mise pins every tool and is the task runner; lefthook runs the checks as git hooks; GitHub Actions runs the -ci variants of the same tasks. Vite builds all three outputs — the page, the server and the CLI — into the plugin folder, with every runtime dependency bundled in, so the plugin runs without an install step. The plugin lives in its own subfolder, which is what a user will install; the marketplace manifest at the repository root points at that folder on a release branch that F12 will produce. A placeholder in each source folder exercises the whole chain, and a short list of points must be proven before anything else is built on top.

The plugin is a subfolder rather than the repository root for two reasons: a user then installs only the plugin, not the sources, documents and tests; and Claude Code warns about a CLAUDE.md at a plugin root, which would fail the strict validation. Unit tests sit next to the code they test as ‹name›.test.ts; end-to-end tests test the whole plugin and therefore live in e2e/. .gitignore also ignores the brainstorming journals (docs/features/*-decisions.md), plugin/dist/ and plugin/evals/results/.

Toolchain and versions

mise.toml pins exact versions of Node 24, pnpm and Claude Code (the npm package @anthropic-ai/claude-code), so every machine and CI run uses the same tools for building and checking; the Claude Code version is the one the README names as “tested with”. Its postinstall hook runs the setup task: pnpm install --frozen-lockfile, playwright install chromium and lefthook install. lefthook itself is a development dependency with an exact version, like every other npm tool. mise only fires postinstall when it installed a tool, hence the separate task for later runs.

pnpm is configured to save exact versions (save-exact) and keeps its minimum release age, which refuses package versions published less than about a day ago. pnpm's strict node_modules only lets code import packages it declares, so nothing undeclared can slip into the bundle. Every direct dependency has an exact version; the lockfile is committed; CI installs with a frozen lockfile and fails if package.json and the lockfile disagree. Exact versions make every upgrade a visible change and satisfy the requirement that server and browser use exactly the same collaboration packages once F05 brings them in.

TypeScript 6, ESM only ("type": "module"). On top of strict: noUncheckedIndexedAccess (an indexed value may be undefined), noImplicitOverride, noImplicitReturns, noFallthroughCasesInSwitch, verbatimModuleSyntax (type imports are explicit) and erasableSyntaxOnly (no enum, namespace or parameter properties, so Node 24 can run scripts directly). exactOptionalPropertyTypes and noPropertyAccessFromIndexSignature are left out: they fight third-party and Vue prop types for little gain. Three configs share the base: tsconfig.node.json for src/cli, src/server and the tool configs, tsconfig.web.json (DOM types) for src/web, and both include src/shared, which therefore may use neither Node nor DOM APIs.

Linting is ESLint with typescript-eslint's type-aware recommended rules and eslint-plugin-vue's recommended rules; eslint-config-prettier turns off rules that formatting covers. Formatting is Prettier for TypeScript, Vue, CSS, JSON, YAML and Markdown outside docs/. .editorconfig sets two-space indentation, LF line endings, UTF-8 and a final newline for every editor; no editor-specific settings are committed.

Build and bundling

One vite.config.ts produces three outputs into plugin/dist/: the page (dist/web/, built for the browser from src/web), the server (dist/server.js) and the CLI (dist/cli.js), both built for Node 24 from src/server and src/cli with every dependency inlined (Vite's server build with nothing left external). One bundler for all three means shared code and libraries are resolved the same way in browser and Node — which matters as soon as a library such as Yjs must exist only once on each side. An installed plugin therefore needs no node_modules and no install step: nothing can fail on the user's machine, and it runs exactly the versions that were tested. Claude Code could install dependencies from a lockfile next to a plugin's package.json, but that would add an install step on every user's machine; plugin/ has no package.json, so it never does.

plugin/bin/tandem is a bash script that runs under the bash 3.2 shipped with macOS. It looks for node, checks that its major version is at least 24 and, if not, prints which version is needed and exits non-zero; otherwise it runs node "$(dirname "$0")/../dist/cli.js" "$@". A plain executable is needed because Claude Code's permission guard was seen refusing input piped into npm run while accepting the same input piped into a plain command (spike 08, branch spike, 08-agent-edit-path/README.md).

Placeholder

tandem serve starts dist/server.js as a child process in the foreground, passes the port on, lets its output through, forwards Ctrl+C and termination signals and exits with the child's exit code. The server listens on 127.0.0.1, port 0 by default so the operating system picks a free port, prints the URL once it is listening, serves the built page and answers GET /api/hello. It uses Node's built-in http module; choosing a server framework, like the process model as a whole, is F01's decision. The separate server bundle keeps the three-output build real; how and when the server process is started for real is designed in F01.

The placeholder exists only so that every tool has something to run on. Each file starts with PLACEHOLDER (F00) — delete in the next feature, the architecture document marks the placeholder as such, and nothing outside the placeholder may import it.

Import rules

.dependency-cruiser.cjs enforces:

  • src/cli, src/server and src/web may import src/shared, but not each other. The CLI starts the built server as a process instead of importing its code.
  • src/shared imports nothing from the other folders and no Node built-ins, because it also runs in the browser.
  • src/web imports no Node built-ins.
  • No circular imports, no orphan modules, and no development-only dependency in code that ships.

These rules run before each commit when src/ changes and in CI. Several of them catch bundling mistakes early — a Node module pulled into the page, a test helper pulled into the plugin.

Git hooks

lefthook.yml defines the hooks of Git hooks. Each command has a glob; lefthook skips the command when no staged (pre-commit) or pushed (pre-push) file matches. A command that receives {staged_files} runs on those files only — formatting and linting, with stage_fixed re-staging what they fixed. A command without a file list runs as written on the whole project — type checking, the import rules, plugin validation and the unit tests. Globs use the doublestar matcher so that top-level files match too. Pre-commit commands run in parallel. CI sets LEFTHOOK=0, since it runs the tasks itself. The skeleton measures a baseline for the time budget — about 10 seconds for the pre-commit hook and about 60 seconds for the pre-push hook — on a typical change: one source file and its test edited.

The -ci variants write their reports to reports/<task>/ and contain nothing specific to GitHub. Unit tests use Vitest with two projects: Node for src/cli, src/server and src/shared, and happy-dom, a simulated DOM, for src/web. Most Vue components can be tested without a real browser; tests that need one — expected for the interactive Tiptap integration in F04 — switch to Vitest's browser mode selectively. End-to-end tests use Playwright Test with Chromium.

Coverage gate

test-ci measures coverage with V8 over src/** (test files excluded). The source folders are listed explicitly in the coverage configuration, because otherwise a file no test imports would not appear in the report at all and would slip past the gate. Thresholds are 80 % lines and 80 % branches, checked per file, limited to files changed since the base: origin/main on a pull request, the parent commit on a push to main (squash merges make that commit the whole pull request).

CI on GitHub

Three workflows:

  • ci.yml, on pull requests to main and pushes to main. Job check on Linux with Node 24 runs mise run check-ci. Job node-latest on Linux with the latest Node LTS (currently 26) runs build and e2e-ci, to notice early when a newer Node breaks something. Both set up the pinned tools with the official mise action, cache the pnpm store and the Playwright browser, and a newer run on the same pull request cancels the older one.
  • pr-title.yml, on pull requests (opened, edited, synchronised): a small script of our own checks the title against type(scope)?: description with the Conventional Commits types. It needs no third-party action, no checkout of the pull request's code and no secret.
  • agent-tests.yml, started by hand or when the maintainer adds the label agent-tests to a pull request. It installs bubblewrap and socat (needed by Claude Code's sandbox on Linux), runs mise run test-agent-ci with the Claude credential from a repository secret, a score threshold and a cost ceiling, and uploads the JSON result. Secrets are never available to pull requests from forks.

Security baseline: the default workflow token is read-only and each job asks only for the permissions it needs; third-party actions are pinned to full commit hashes, not movable tags; the Claude credential is used only in agent-tests.yml. Repository settings: a ruleset on main that requires a pull request, requires the checks check, node-latest and pr-title, allows only squash merges and blocks force pushes and deletion; secret scanning with push protection; Dependabot alerts (not update pull requests, which are F12's). Creating the repository, pushing main and spike, and applying these settings are implementation steps done with the maintainer, since they publish to GitHub.

Plugin and marketplace

plugin/.claude-plugin/plugin.json names the plugin (working name), with description, author, licence and repository. The repository root's .claude-plugin/marketplace.json lists one plugin whose source is a git-subdir: this repository, path plugin, ref release. Users add the marketplace from the default branch and install the plugin from the release branch, where F12's release workflow will commit the built dist/; on main, dist/ is never committed. No minimum Claude Code version can be declared in a manifest; the README states the version the project is tested with, and a later feature that needs a minimum checks it in its hooks.

claude plugin validate --strict runs on plugin/ and on the repository root, which validates the marketplace. Agent-test cases live in plugin/evals/, the only place claude plugin eval accepts (its directory must lie inside the plugin root); whether the release drops them is F12's call. The placeholder case asks Claude to greet using the plugin and is graded by a deterministic check that Claude ran tandem hello, without a judge model.

Building blocks

The repository as a whole, minus configuration, CI and documents, which Solution design describes. Its building blocks are the source code in src/, the plugin folder in plugin/ that the source is built into, and the end-to-end tests in e2e/. Everything in src/ and the plugin's stub skill, hook and agent-test case is placeholder and is deleted by the next feature; what stays is the structure — the folders, their import rules and the plugin layout.

src/ does not depend on plugin/ at code level: the build writes its output into plugin/dist/. The end-to-end test uses plugin/ exactly as Claude Code will, through bin/tandem, so it also covers the entry point and the bundles.

e2e/ — e2e/hello.spec.ts starts plugin/bin/tandem serve, reads the URL from its output, opens it in Chromium, waits for the greeting from GET /api/hello and stops the process. It is a test with no interface of its own, and placeholder like everything it tests; playwright.config.ts and the fixtures pattern for starting the CLI stay.

src/

All source code, one folder per runtime environment: cli/ and server/ run in Node, web/ in the browser, shared/ in both. Each folder below is placeholder; the folders and their import rules (Import rules) are permanent.

Each entry module (main.ts) only wires its folder's module to the process or page. The three environment folders import shared/ and nothing of each other; cli.ts reaches the server only by starting its built bundle, which keeps the CLI bundle free of server code and leaves the process model to F01. greeting.ts depends on product.ts, the one place the working name lives in code.

cli/

The command-line interface Claude and the end-to-end test call through plugin/bin/tandem; built into dist/cli.js.

cli/main.ts — entry of dist/cli.js. Calls runCli(process.argv.slice(2), process.stdout) and exits with the returned code. No exports.

cli/cli.ts — the placeholder commands, testable without spawning anything when serve is not called.

runCli(argv: string[], out: Writable): Promise<number> — hello [name] writes greeting(name ?? "world") to out and returns 0. serve [--port n] starts node dist/server.js --port n (path resolved next to the running cli.js) as a child process with inherited output, forwards SIGINT and SIGTERM to it and resolves with its exit code. Unknown commands write a short usage text and return 2.

server/

The local HTTP server; built into dist/server.js and started by tandem serve.

server/main.ts — entry of dist/server.js. Reads --port (default 0), calls startServer with the built page folder next to it, prints ‹PRODUCT_NAME› placeholder running at ‹url› and calls close() on SIGINT or SIGTERM before exiting with 0. No exports.

server/server.ts — a minimal HTTP server on Node's http module, bound to 127.0.0.1.

startServer(options: StartOptions): Promise<RunningServer> — listens on options.port; answers GET /api/hello with 200 { "message": greeting("world") } as JSON, serves files from options.webRoot for every other GET (index.html for /, 404 for missing files and for paths that leave webRoot), and answers other methods with 405. Resolves once listening. StartOptions is { port: number; webRoot: string }; RunningServer is { url: string; close(): Promise<void> }, where url carries the actual port and close stops accepting connections and resolves when the server is closed.

web/

The page the server delivers; built into dist/web/.

web/main.ts — entry of dist/web/. Creates the Vue app with App.vue and mounts it. No exports.

web/App.vue — the placeholder page, a component without props. On mount it fetches /api/hello and shows the message, or “Server not reachable” if the request fails; the note “Placeholder page (F00)” sits below it. A few lines of plain scoped CSS.

shared/

Code that runs in Node and in the browser; imported by the three other folders and built into each of their outputs.

shared/greeting.ts — greeting(name: string): string returns Hello, ‹name› — from ‹PRODUCT_NAME›. Pure, no I/O.

shared/product.ts — PRODUCT_NAME: string, the working name "tandem". Renaming changes this constant and the file names and manifests listed in Renaming.

plugin/

The plugin root: exactly what a user installs and what --plugin-dir loads. Its structure is permanent; the stub skill, the hook and the agent-test case are placeholder. It contains no code of its own — the CLI, server and page come from src/ through the build — so its parts are files.

.claude-plugin/plugin.json — the manifest: plugin name (working name), description, author, licence, repository. The plugin's components sit in their default folders, so the manifest lists no paths.

bin/tandem — the entry point Claude and the end-to-end test call; on the Bash PATH while the plugin is enabled. Checks for Node ≥ 24 and runs dist/cli.js with all arguments (Build and bundling).

skills/tandem/SKILL.md — stub skill: when the user asks for a greeting from the plugin, run tandem hello and show the output. Replaced by F10's real skill.

hooks/hooks.json — one hook on session start that appends a timestamp line to a file under ${CLAUDE_PLUGIN_DATA}, proving that the plugin's hooks fire in a real session. Replaced by F10.

evals/hello/ — the agent-test case: the prompt asks Claude to greet the user using the plugin; one tool_used grader checks that Claude ran tandem hello.

dist/ — build output (cli.js, server.js, web/); ignored on main, committed only on the release branch by F12.
