F08 · Comments specification pending

Threads on text, blocks, diagrams or the whole document — sent to Claude, answered in place.

Overview

Comments live next to the text (Yjs relative positions in a comments map), never as markup in the HTML, and are mirrored to .collab/<doc>.comments.json. The server turns them into events for collab wait; the agent answers with collab reply / resolve, visible live in the margin. The spike data model is an artefact — this feature needs a proper design phase.

What the spikes settled

  • Relative-position anchors survive concurrent edits, overlaps and block/diagram comments; a mark inside the text doesn't (06, 14 scenarios).
  • Re-anchoring by stored quote inside the same block after agent edits (06).
  • Event queued 4 ms after the comment; wait exits ~420 ms later, 400 ms of it the settle window (06).
  • Spike recommendation: review round by default, “Ask agent” immediate (06) — still a decision for you.

Open / to decide

  • Thorough design of the data model: kind vs ask, two author shapes, delivery state over four fields (N12).
  • Intent per thread entry, not per thread (N22); document-level comments (N16); threads tracking the changes made for them (N17).
  • Events as pointers, not work packages — don't narrow the agent's view (N11).
  • Comments on journal entries are events only; doc id so comments survive renames (06, 09).
