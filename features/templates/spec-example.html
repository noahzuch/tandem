X01 · Link shortener

Status: Final

Goal

Employees share long internal URLs — dashboards, tickets, search results — in chat, slides and printed notices. These URLs wrap across lines, break when copied, and can't be read out in a meeting. Nobody can tell whether a shared link is actually used.

With the link shortener, anyone in the company turns a long URL into a short one like go.example/k7Qa2B from the intranet portal, the short link opens the original page, and the creator sees how often each of their links was opened.

Non-goals

  • Custom short codes (go.example/sales-q3): they need naming rules and conflict handling between teams; the portal team may request it later.
  • Editing or deleting links: a short link that was printed or pasted must keep pointing where it pointed. This also lets the service cache links forever (see Redirect).
  • Private links: codes are sequential and therefore guessable (see Short codes). Secret URLs must not be shortened.
  • Per-visitor analytics: no IP addresses, user agents or visitor identities are stored, so the service holds no personal data about visitors.
  • Use from the public internet: the service is reachable only inside the company network.

Functional design

People manage their links on a “Short links” page in the intranet portal: they paste a long address, get a short link to copy, and see all their links with how often each was opened. Whoever receives a short link simply opens it — there is nothing to log in to or install, and visitors never see the shortener itself.

Creating a short link

The user pastes an address and presses Shorten; the short link appears right below the field with a Copy button. If they have shortened the same address before, they get their existing link back with the note “You already had a short link for this address”. Repeating the action therefore never clutters their list, and a link they shared earlier stays the one to use. Addresses that differ only in the capitalisation of the domain or in a default port count as the same address.

Only web addresses (http, https) of up to 2,048 characters are accepted. Anything else shows “This doesn't look like a web address” and creates nothing. Short links always have six characters, mixing digits and upper- and lowercase letters, so they must be copied, not retyped from memory.

My links

Below the form, the user sees every link they created, newest first, with its target, creation date and how often it was opened. The counts can be up to a minute behind, because visits are collected and saved in batches (Click counting). Each person sees only their own links. Links can't be edited or deleted (see Non-goals).

Opening a short link

Opening a short link leads straight to the target page. Every visit is counted for the creator, but nothing about the visitor is recorded. A short link that doesn't exist — usually a typo — never leads anywhere; it shows a “Link not found” page instead.

Context

The link shortener is a small backend service. People don't use it directly: they create links in the intranet portal, which owns the user interface, and they open short links in their browser. The company reverse proxy terminates TLS for go.example and forwards all traffic. The service relies on the company SSO for user identity and on a PostgreSQL database run by the platform team.

Assumptions and constraints

  • At most 10,000 new links and 500,000 redirects per day; redirects outnumber new links by far. If load grows tenfold, the single instance below must be revisited.
  • The service runs as exactly one instance. Click counts are held in memory before they are written (see Click counting), which would need a shared counter with several instances.
  • Only the reverse proxy can reach the service, so the redirect endpoint needs no authentication.

Solution design

Every new link gets the next number from a database sequence, and its short code is that number written in base 62 — unique by construction, so no collision checks are needed. A redirect looks the code up in an in-memory cache first and in the database only on a miss; because links never change, cached entries never go stale. Clicks are counted in memory and written to the database in one batch every 30 seconds, so a redirect never waits for a database write.

Data model

All state is one table. The sequence behind id starts at 625 = 916,132,832 for the reason given in Short codes.

Short codes

Shortening first normalises the URL — lowercase scheme and host, default ports removed, path, query and fragment kept as they are — so that trivially different spellings of one address count as the same URL. If the user already owns a link for the normalised URL, that link is returned (Creating a short link). Otherwise the service takes the next sequence number and encodes it in base 62 with the alphabet 0–9 a–z A–Z.

The sequence starts at 625 because that is the smallest number with six base-62 digits: every code is exactly six characters (100000 for the first link) until 626 ≈ 56.8 billion links, instead of growing from one character. Consecutive numbers make codes guessable; that is accepted because links are not secret (see Non-goals).

Redirect

A redirect resolves the code through an in-memory cache of the 10,000 most recently used links, falling back to the database on a miss. Because links are never edited or deleted, a cached entry is valid forever and the cache needs no invalidation. Unknown codes are not cached, so each one costs a database lookup; at the assumed load that is cheap, and it avoids filling the cache with typos.

The response is 302 Found, not 301 Moved Permanently: browsers cache a 301 for good and would open later clicks without asking the service, so those clicks would never be counted (My links).

Click counting

Writing a counter row on every redirect would put a database write into every redirect and make concurrent redirects of a popular link wait on the same row. Instead, each redirect only increments a number in an in-memory map. Every 30 seconds — and once more when the service shuts down — the map is swapped for an empty one and its contents are written in a single batch. If the write fails, the counts are merged back into the live map and retried with the next batch. A crash loses at most the last 30 seconds of clicks; the counts in My links are at most a minute behind.

Building blocks

The link shortener is one Node.js (TypeScript) process; its code lives in src/. To its users it is four HTTP endpoints, called by the intranet portal, by browsers and by the reverse proxy.

POST /api/links(body: { url: string }): 201 | 200 { code: string, shortUrl: string } — creates a short link for the calling user. api/ checks the SSO token (401 without one) and the URL (400 if it isn't a web address), then core/ returns the caller's existing link (200) or creates a new one in storage/ (201).

GET /api/links(): 200 LinkSummary[] — the caller's links, newest first, as { code: string, url: string, createdAt: string, clicks: number }. Requires the SSO token. Click counts come from the database and are therefore up to 30 seconds behind.

GET /:code(): 302 | 404 — the redirect. core/ resolves the code from its cache or storage/ and counts the click in memory; api/ answers 302 with the target URL, or the “not found” page with 404.

GET /healthz(): 200 | 503 — for the reverse proxy. main.ts answers 200 if the database answers a trivial query, 503 otherwise.

main.ts creates and connects the other three parts. api/ calls core/. storage/ depends on core/, not the other way round: core/ declares the repository interface it needs, and storage/ implements it for PostgreSQL. This keeps the rules of the service — shortening, resolving, counting — free of database code, so they can be tested against an in-memory repository.

main.ts — the entry point. It reads the configuration from environment variables, opens the database, runs the migrations, creates the repository, the core services, the API classes and the HTTP server, registers the routes and /healthz, and starts the click counter. On SIGTERM it stops accepting requests, then stops the click counter (which writes its last batch) and closes the database.

api/

The HTTP layer (src/api/, built on Fastify). It translates requests into calls to core/ and results into responses; it contains no business rules.

LinkController handles all three routes and asks Auth who is calling for the two that need a user; the redirect is public (see Assumptions). main.ts creates both and passes Auth into the controller.

LinkController — maps the three routes to the core services.

constructor(links: LinkService, resolver: LinkResolver, clicks: ClickCounter, auth: Auth) — keeps its collaborators; it holds no other state.

register(app: FastifyInstance): void — registers shorten for POST /api/links, list for GET /api/links and redirect for GET /:code, with auth.authenticate as a pre-handler on the two /api/* routes.

shorten(req: FastifyRequest, reply: FastifyReply): Promise<void> — rejects anything but an http/https URL of up to 2,048 characters with 400, then calls links.shorten(url, req.owner). Answers 201 if the result is new and 200 if the link already existed (Creating a short link), with { code, shortUrl }, where shortUrl is https://go.example/ plus the code.

list(req: FastifyRequest, reply: FastifyReply): Promise<void> — calls links.listOwned(req.owner) and answers 200 with each link mapped to { code, url, createdAt, clicks }, createdAt as an ISO date.

redirect(req: FastifyRequest, reply: FastifyReply): Promise<void> — asks resolver.resolve(code) for the URL; if there is none it renders the “not found” page with 404, otherwise it calls clicks.increment(code) and answers 302 (the reason for 302 is in Redirect).

Auth — checks who is calling.

constructor(jwksUrl: string) — keeps the URL of the SSO's public signing keys; the keys are fetched on first use and refreshed hourly.

authenticate(req: FastifyRequest): Promise<void> — verifies the SSO token in the Authorization header against the signing keys and sets req.owner to the token's subject. A missing or invalid token ends the request with 401.

core/

The rules of the service (src/core/): creating links, resolving codes and counting clicks. It does no I/O of its own; everything persistent goes through the LinkRepository interface.

The three services each serve one kind of request and don't call each other; all of them read and write through LinkRepository. Defining that interface here, where it is used, is what lets the dependency point from storage/ to core/.

LinkService — creates links and lists a user's links.

constructor(repo: LinkRepository) — keeps the repository; the service holds no other state.

shorten(url: string, owner: string): Promise<ShortenResult> — normalises the URL (Short codes) and returns { link, created: false } if repo.findByOwnerAndUrl finds the owner's link for it. Otherwise it takes repo.nextId(), encodes the id in base 62 — dividing by 62 repeatedly and mapping each remainder to a character of 0–9 a–z A–Z, most significant digit first — and stores the link with repo.insert, returning { link, created: true }. ShortenResult is { link: Link, created: boolean }.

listOwned(owner: string): Promise<Link[]> — returns repo.listByOwner(owner) unchanged; the ordering (newest first) is part of the repository's contract.

LinkResolver — turns codes into target URLs, with a cache in front of the repository.

constructor(repo: LinkRepository, cacheSize: number) — creates an empty LRU map holding at most cacheSize links (10,000 in production).

resolve(code: string): Promise<string | null> — on a cache hit returns the URL and marks the entry as most recently used. On a miss it asks repo.findByCode; a found link is cached (evicting the least recently used entry when full) and its URL returned, an unknown code returns null and is not cached (Redirect).

ClickCounter — counts clicks in memory and writes them in batches (Click counting).

constructor(repo: LinkRepository, flushMs: number) — creates the empty count map; flushMs is the batch interval (30,000 in production).

increment(code: string): void — adds one to the code's count in the map. Synchronous and without I/O, so a redirect never waits for it.

start(): void — starts a timer that flushes every flushMs. A flush swaps the map for an empty one and passes the old one to repo.addClicks; if that fails, it adds the counts back into the live map so the next flush retries them.

stop(): Promise<void> — clears the timer and runs one last flush; resolves when it has been written.

LinkRepository — the persistence contract the services need; tests use an in-memory implementation, production uses storage/. nextId never returns the same id twice; insert takes a NewLink ({ id, code, url, owner }) and returns it as a Link with createdAt set and clicks 0; the two find… methods return null when nothing matches; listByOwner returns newest first; addClicks adds each count to its link, all or nothing.

Link — one row of the links table (Data model) as an object; every part passes links in this shape. id is the sequence number the code was derived from, code the short code, url the normalised target URL and owner the SSO subject of the creator; createdAt is set by the database on insert, and clicks is the click count as of the last batch write (Click counting).

storage/

Everything PostgreSQL-specific (src/storage/): the repository implementation, the connection pool and the schema migrations.

Both the repository and the migrations reach the database only through Database. main.ts runs the migrations before the HTTP server starts, so the repository always finds the schema it expects.

PgLinkRepository — implements LinkRepository with one SQL statement per method.

constructor(db: Database) — keeps the database; all statements go through it.

nextId(): Promise<number> — SELECT nextval('links_id_seq').

insert(link: NewLink): Promise<Link> — INSERT … RETURNING *, so createdAt and clicks come from the column defaults.

findByCode(code: string): Promise<Link | null> — a lookup on the unique index of code.

findByOwnerAndUrl(owner: string, url: string): Promise<Link | null> — a lookup on the unique index of (owner, url).

listByOwner(owner: string): Promise<Link[]> — WHERE owner = $1 ORDER BY created_at DESC.

addClicks(batch: Map<string, number>): Promise<void> — one UPDATE links SET clicks = clicks + v.n FROM (VALUES …) AS v(code, n) WHERE links.code = v.code, so a flush is one round trip however many links it covers, and a single statement is all or nothing.

Database — the only owner of database connections.

constructor(url: string) — creates a pg connection pool of 10 connections for url.

query<T>(sql: string, params: unknown[]): Promise<T[]> — runs one statement on any free connection and returns its rows.

transaction<T>(fn: (tx: Database) => Promise<T>): Promise<T> — takes one connection, runs BEGIN, calls fn with a Database bound to that connection, and commits when fn resolves or rolls back when it throws.

close(): Promise<void> — waits for running queries and closes the pool.

migrate.ts — applies the numbered SQL files in src/storage/migrations/. The first one creates the links table and its sequence (Data model).

runMigrations(db: Database): Promise<void> — reads the SQL files, skips those recorded in the schema_migrations table, and applies the rest in order, each in its own transaction together with its record, so a failed migration leaves no trace.
